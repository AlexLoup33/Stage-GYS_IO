\subsection{Parallel File Systems and Data Striping}
\label{sec:pfs}

Traditional file systems rely on single storage controllers, which creates a severe
bottleneck when thousands of parallel processes attempt simultaneous file access.
PFS---such as Lustre, BeeGFS, and GPFS---bypass this bottleneck by partitioning 
files across multiple independent storage devices via data striping.

In such systems, storage capacity is divided into logical entities called Object
Storage Targets~(OSTs). An OST represents a dedicated physical storage unit
(e.g., a RAID array or NVMe volume) managed by an Object Storage Server~(OSS).
Metadata servers~(MDS) maintain directory structures and file layouts, while OSTs
handle actual data payload transfers.

Data striping partitions a logical file stream into contiguous blocks of size
$S_{\text{stripe}}$ (stripe size). These blocks are distributed in a round-robin
sequence across $N_{\text{OST}}$ targets (stripe count). For example, with
$N_{\text{OST}} = 4$ and $S_{\text{stripe}} = 1$~MB, the first megabyte is written
to OST~0, the second to OST~1, and so on. Striping allows applications to aggregate
the physical bandwidth of multiple storage devices, ideally achieving an
$N_{\text{OST}}$-fold increase in overall write throughput. However, the actual
gain depends heavily on the alignment between the stripe configuration and the
application's access pattern, which motivates the tuning study presented in
Section~\ref{sec:results}. Figure~\ref{fig:striping} illustrates this process
for this example.

  \includegraphics[width=0.8\textwidth]{figures/striping.png}
  \caption{Striping in a parallel file system. A file created on a compute node is
           split into fixed-size chunks, which are written in parallel to the storage

           the stripe size is 1~MB: each colour is one OST, and the chunks are
           distributed round-robin.}
  \label{fig:striping}
\end{figure}

The stripe count and the stripe size are configuration parameters rather than
fixed properties of the file system, although how much of that control reaches the
end user depends on the deployment: Lustre lets any user set the layout of the files
and directories they own (through \texttt{lfs setstripe}), whereas on other systems
the striping policy is a global default that only the administrator can change.
Where users are allowed to set it, the layout is inherited from the parent directory:
a file is created with the stripe count and stripe size of the directory that holds
it, and that layout is then fixed for the lifetime of the file. Evaluating several
striping configurations therefore amounts to creating one directory per configuration
and writing into each of them, which is the approach followed throughout this report.

\subsection{Parallel Write Strategies}
\label{sec:strategies}

When an application needs to store data, it calls the PFS with a file name. However,
as seen earlier, the PFS splits the file in blocks and hides other optimizations
(such as buffers) to improve I/O performance. An application thus has several ways,
depending on its data and needs, to create files and store this data. What a write
strategy defines is the mapping between the data held in memory by the processes of the
parallel application (MPI processes in \textsc{Gysela}) and the files that end up on the PFS: how many files a checkpoint is made of, which processes
contribute to each of them, and whether those processes write collectively or
independently. Many such mappings exist; the three strategies considered here, and
their names, are our own distinction rather than a convention of the domain.

Two quantities matter in such a mapping: the number of files created, and the number
of processes writing into each of them. Tuning an I/O comes down to a trade-off
between the two. Concentrating the output in a few files keeps the metadata load low,
but forces processes to share the same file, where concurrent writes to the same regions
serialise on file system locks; spreading it over many files removes that contention,
but multiplies the metadata operations and the number of objects the file system has
to track. Tuning the I/O therefore consists in first checking that each process
writes large contiguous blocks, then in choosing the balance between the number of
files and the number of processes per file. The mapping also interacts with the striping parameters of
Section~\ref{sec:pfs}: a single shared file only exploits several OSTs if its stripe
count allows it, whereas with one file per process the files are spread
over the targets by themselves, on top of whatever striping is applied to each of them. In this work,
we analyze three I/O strategies, all implemented via the Parallel Data
Interface~(PDI) middleware (described in Section~\ref{sec:tools}), a layer that
decouples the application from the I/O library: the strategy and its parameters
are selected in an external YAML configuration file rather than in the source code. All
three strategies therefore exercise the same \texttt{gys\_io} code path and differ
only in the file layout they produce, which is what makes the comparison in
Section~\ref{sec:results} a comparison of layouts rather than of implementations.

\paragraph{Single Shared File}
\label{sec:ssf}
In the Single Shared File~(SSF) approach, all processes concurrently write
their local data slices into a single unified file on the PFS
(Figure~\ref{fig:ssf_schema}). Standard libraries such as HDF5 or MPI-IO employ
two-phase I/O to aggregate non-contiguous memory layouts into large, contiguous
file offsets before issuing collective storage calls. While SSF simplifies dataset
management by producing a single output file, it can suffer from locking contention
on storage targets when the number of concurrent writers scales up.
SSF is also the strategy for which the striping parameters
matter most: because the whole checkpoint lives in one file, the number of OSTs that
serve it is exactly its stripe count, so a low stripe count caps the
achievable bandwidth no matter how many processes write in parallel. The stripe size
should also be a multiple of the write size of each process, so that a process does not
write on several OSTs.

\paragraph{File Per Process}
\label{sec:fpp}
In the File Per Process~(FPP) approach, every process creates and writes its
own separate file independently (Figure~\ref{fig:fpp_schema}). Because no
inter-process communication or offset synchronization is required, local write
throughput can be very high, as each process accesses its file without contention.
However, FPP generates $N_{\text{procs}}$ separate files per checkpoint, which can
strain metadata servers at scale and complicate downstream post-processing and data
management. Whether the throughput advantage of FPP outweighs these drawbacks at
production scale is one of the questions addressed in Section~\ref{sec:results}.
Because all processes create their files at the same instant, every checkpoint reaches
the metadata servers as a burst of simultaneous file creations, so the number of
requests the MDS has to handle becomes very large. This is also likely to create
network contention, although this is not the main topic of this work. Wang et
al.~\cite{wang2018mitigating} reduce this kind of contention by stalling some processes
for a random time.

\paragraph{Subfiling}
\label{sec:subfiling}
Subfiling acts as an intermediate approach between SSF and File Per Process.
Processes are partitioned into distinct sub-groups. Within each group, an
assigned process---referred to as an I/O Concentrator~(IOC) or aggregator---collects
data from its peer processes and writes it to a dedicated subfile
(Figure~\ref{fig:subfiling_schema}). Like the two-phase I/O used by SSF, this relies
on aggregating the data of several processes before writing, the difference being that
each aggregator writes its own file. This reduces file system lock contention
compared to SSF while avoiding the metadata overload associated with generating one
file per process. The total number of subfiles ($N_{\text{subfiles}}$) is a tunable
parameter; its interaction with the physical OST count is one of the central
questions examined in this study.
This parameter interpolates between the two previous strategies: with a single
subfile the scheme degenerates into SSF, and with as many subfiles as processes it becomes
FPP, so the useful configurations lie in between, typically one subfile per node or one
per OST. The aggregation step is what buys the reduction in contention, as each IOC
gathers the slices of its group and issues fewer, larger and contiguous writes instead
of many small interleaved ones. That gain is not free: the collection phase adds a
communication step before any data reaches the storage system, and the bandwidth of a
group is limited by the single IOC that serves it.

\subsection{Software Stack and Tooling}
\label{sec:tools}

Our experimental framework relies on four key software components, which together
enable systematic and reproducible evaluation of the I/O strategies described above.
\texttt{gys\_io} is the application actually executed in the experiments: a
mini-application that reproduces \textsc{Gysela}'s 5D checkpoint writes without its
physics, so that a full parameter sweep costs a fraction of a production simulation.
HDF5 is the format these checkpoints are written in, and the library that calls the
PFS and stores the data, for all three strategies. PDI sits between the two: an
interface that calls I/O libraries such as HDF5. It decides, from an external
YAML configuration file, which library and which strategy a given run uses, which is what
makes it possible to compare the three strategies without modifying the application.
IOPS drives the campaigns themselves, generating the parameter sweeps, submitting the
jobs to the batch scheduler and collecting the resulting measurements. Each of these
components is described in more detail below.

\paragraph{\texttt{gys\_io} Mini-Application}
\label{sec:gysio}
\texttt{gys\_io}~\cite{gysela_miniapp_io} is a lightweight benchmark proxy
developed by CEA outside the main \textsc{Gysela} code base, to focus only on the I/O
phases (and compression, which we do not study here). It replicates \textsc{Gysela}'s
5D domain decomposition and checkpoint write calls while skipping all computational
physics routines. It reads \textsc{Gysela} configuration files directly, which makes
it possible to reproduce the application's I/O access patterns across different grid
configurations and process topologies without incurring the cost of full plasma
simulations. Its small footprint and short execution time make it well-suited for
large parameter sweeps, which is the primary mode of use in this study.

\paragraph{HDF5}
\label{sec:hdf5}
The Hierarchical Data Format version~5~(HDF5)~\cite{folk2011overview} is the output format used
by both \textsc{Gysela} and \texttt{gys\_io} for checkpoint files. HDF5 is a
self-describing binary format designed for storing and organizing large, complex
datasets in a portable and efficient manner. It provides a high-level API that
supports parallel I/O through MPI-IO, enabling collective and independent write
modes. In the context of this study, HDF5 serves as the I/O layer beneath all three
strategies; its collective write mode is particularly important for
SSF, where all processes coordinate to produce a single consistent output file. For the
FPP strategy, each process produces an independent HDF5 file, which requires
post-processing to reconstruct the full dataset.

\paragraph{Parallel Data Interface (PDI)}
\label{sec:pdi}
PDI~\cite{roussel2017pdi} is a data interface middleware that decouples application I/O code
from the underlying storage libraries. Rather than hardcoding I/O calls within the
application source, \texttt{gys\_io} delegates all data transfers to PDI. The I/O is
described in an external YAML configuration file, which states, for each I/O, the
backend (the I/O library, here HDF5), the target file, which data is written, and
where in the file. The target file is what allows us to vary the stripe count, and since
the description is given per I/O, different libraries can be used for different I/O
(e.g., checkpointing and post-processing). According to this description, HDF5
performs collective writes for SSF, subfiling, or independent per-process writes for
FPP. This design allows switching between strategies
and tuning their parameters without recompiling the application binary, which is
essential for conducting systematic benchmark campaigns. PDI thus acts as the
central control point for all I/O strategy selection in our experiments.

\paragraph{IOPS Benchmark Automation Framework}
\label{sec:iops}
IOPS~\cite{iops_tool} is a benchmark automation framework developed within the TADaaM team at Inria
Bordeaux. It is designed to facilitate large-scale I/O benchmark campaigns by
automating parameter sweeps over configurations such as stripe count, stripe size,
number of subfiles, I/O strategy, and process topology. IOPS generates and submits
SLURM batch scripts, monitors job execution on the target cluster, and collects
performance metrics---in our case \texttt{time\_write}, \texttt{total\_time} and
\texttt{bandwidth}---into structured output files. Beyond raw data collection, IOPS also
produces preliminary result reports, providing an immediate first visualization of
performance trends across the parameter space. This capability significantly reduces
the manual effort required to analyze large sets of experiments and supports
iterative refinement of the benchmark campaign.
