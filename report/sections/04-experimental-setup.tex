\section{Experimental Setup}
\label{sec:setup}
% ==============================================================================

To evaluate the performance and scalability of our parallel I/O strategies, we conducted
experiments on two distinct High-Performance Computing (HPC) clusters: Adastra, a national
supercomputer on which all main results are obtained, and Plafrim, a regional cluster used at a
smaller scale to validate the methodology and to check whether the observed trends hold on a
different parallel file system.

\subsection{Target Platforms and Storage Infrastructure}
\label{sec:platforms}

\subsubsection{Prototyping Environment: Plafrim}
\label{sec:plafrim}

The first phase of our experiments took place on the Plafrim~\cite{plafrim_inria} cluster at
Inria Bordeaux. Benchmarks were deployed on the Bora compute nodes, which are equipped with
dual-socket Intel Xeon Gold 6240 processors (36 physical cores per node at 2.60~GHz) and 192~GB of
RAM per node. Inter-node communications rely on an Intel Omni-Path network delivering 100~Gb/s.
Storage on Plafrim is managed by a BeeGFS~\cite{chowdhury2019characterization} parallel file system
configured with up to 8 active Object Storage Targets (OSTs).

\subsubsection{Production Environment: Adastra}
\label{sec:adastra}

To evaluate our strategies at a larger scale, we extended our benchmark campaign to the
Adastra~\cite{adastra_cines} supercomputer at CINES. Tests were run on the GENOA CPU partition,
which features dual-socket AMD EPYC 9654 processors (192 physical cores per node and high memory
throughput). Nodes are connected by an HPE Slingshot-11 high-speed network. Adastra provides two
Lustre file systems, both based on ClusterStor E1000 SSD storage: Home, with a capacity of
125~TiB and a bandwidth of 77~GiB/s in read and 34~GiB/s in write, and Scratch, with a capacity of
1.89~PiB and a bandwidth of 1086~GiB/s in read and 786~GiB/s in write. All checkpoints in this
work are written on Scratch, which is the file system used by production runs. Scratch is
composed of 64 OSTs, which allows fine-grained data striping up to a stripe count of 64.

\subsection{Software Stack and Reproducibility}
\label{sec:repro}

Ensuring reproducible I/O measurements requires strict control over the software environment.
On both platforms, the benchmark applications and I/O middleware were compiled using GCC 13.2.1 \&
OpenMPI \textbf{[TODO: version of OpenMPI]}. The I/O stack relies on PDI version 1.11.0
\textbf{[TODO: commit]} and HDF5 version \textbf{[TODO: version of HDF5]}, with parallel I/O
(MPI-IO) and \texttt{H5FD\_SUBFILING} explicitly enabled. \texttt{gys\_io}, IOPS and Lustre are used
in versions \textbf{[TODO: gys\_io commit, IOPS version, Lustre version]}.

To mitigate NUMA effects and ensure consistent execution, processes were pinned to physical cores
using \texttt{--bind-to core}. For the Subfiling strategy, the I/O Concentrators were allocated and
distributed with a strict mapping of one aggregator per compute node, thereby distributing the
aggregation workload evenly across the allocated infrastructure and avoiding intra-node
bottlenecks. As a consequence, the number of subfiles cannot exceed the number of nodes.

\subsection{Evaluation Methodology and Metrics}
\label{sec:methodology}

To systematically explore the performance landscape, we varied both file system layouts and
write strategies:
\begin{itemize}
  \item \textbf{PFS striping on Plafrim (BeeGFS):} stripe counts ($N_{\text{OST}}$) were evaluated
        from 1 up to the maximum of 8 available targets, with a stripe size ($S_{\text{stripe}}$)
        of 512~KB.
  \item \textbf{PFS striping on Adastra (Lustre):} to capture scalability trends and inflection
        points, stripe counts were scaled up to 64 OSTs, with $N_{\text{OST}} \in \{1, 2, 4, 8, 16,
        32, 40, 64\}$. The stripe size is first fixed to 8~MB, then varied from
        \textbf{[TODO: range, e.g. 1 to 16~MB]} in a dedicated study (Section~\ref{sec:results}).
  \item \textbf{Write strategies:} Single Shared File (SSF), File Per Process (FPP), and Subfiling.
        For Subfiling, the number of subfiles ($N_{\text{subfiles}}$) was tuned between 1 and
        \textbf{[TODO: maximum, e.g. 128]}, with one subfile per aggregator.
\end{itemize}

All benchmarks were submitted in exclusive node allocation mode via Slurm. To maintain a constant
density and mitigate intra-node contention, we allocated 8 processes per node across process
scales ranging from \textbf{[TODO: 16 processes (2 nodes)]} up to \textbf{[TODO: 2048 processes
(256 nodes)]}.

To account for background network and storage noise inherent to shared production file systems,
each experimental configuration was executed 5 independent times, and the output directory was
emptied before each run so that the measured size is exactly that of one checkpoint.

Since the checkpoint is a blocking operation in \textsc{Gysela}, the relevant duration is the time
up to the completion of the global write operation across all processes, denoted $t_{\text{write}}$
(\texttt{time\_write}). The performance metric extracted by the IOPS framework is the write
bandwidth, defined as the total size of the output files, in GiB, divided by $t_{\text{write}}$.

with IOR on the same number of OSTs. Throughout Section~\ref{sec:results}, we report the mean
bandwidth across the 5 runs, with the standard deviation as error bars.
